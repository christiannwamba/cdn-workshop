R32 / First-party browser exercise

Your browser sends the cookie.
The CDN serves the content.

Set a synthetic cookie, send the same content URL again, and compare the browser’s response with genuine signed platform logs.

Before you start

Open Developer Tools → Network. Leave Disable cache unchecked. Filter by /demo/run-. Changing A to B here demonstrates changing cookie state in one browser, not two independent people.

1 / Prepare once

A fresh session gets one shared content URL.

Preparation registers evidence access without fetching content. Sessions last ten minutes and allow twelve one-use request tickets. Cookies and access keys are never placed in URLs or local storage.

No session prepared.

Use the same session in a second isolated browser

Only for this synthetic lab: copy the run ID and temporary session key into another browser’s lab on the exact same host. Separate browser profiles provide independent cookie jars; two ordinary tabs do not. Reset closes the shared session and clears cookies only in the browser where Reset was clicked.

2 / Choose what the browser will send

Set the cookie before each request.

workshop_choice is intentionally JavaScript-accessible test data, scoped to this session’s exact /demo/run-… path with Secure; SameSite=Strict. This is not an authentication-cookie recommendation. An unrelated synthetic cookie is set alongside it to test exclusion.

Choose a case after preparing a session.

  • A: fixture-A → the first request should MISS and create one origin fill.
  • B: fixture-B → the same URL should HIT, with B in the current request’s cookie emission.
  • Missing: selected cookie removed → HIT, cookieState=missing, cookie=null.
  • Invalid: rejected synthetic value → HIT, cookieState=invalid, cookie=null.

The selection label records your intended action. Only the browser Network panel and delivered Middleware emission establish what was actually sent. If you start with B, it becomes the fill request; the first successful request determines MISS/HIT expectations.

Run all prepares a fresh session, then performs the same JavaScript cookie writes and browser fetches for A → B → Missing → Invalid. It never calls the hosted four-request driver.

Pause, expired ticket and repeated-send controls

A request ticket normally lasts sixty seconds; the session lasts ten minutes. Reserving a short ticket lets you verify expiry without waiting ten minutes. An expired or reused ticket is rejected before content access. A fresh ticket keeps the same content URL.

Ready to prepare a session.

3 / Inspect actual requests

Browser receipts and platform evidence.

In Network, select each /demo/run-… request. Under Request Headers / Cookies, compare workshop_choice. Under Response Headers compare x-vercel-cache, x-workshop-event-id, and x-workshop-fill-id.

All requests use the same URL with ordinary fetch caching. The response has max-age=0, so a browser must contact the network again; the shared CDN lifetime is separate. A browser “memory cache” or “disk cache” response is not proof of a new CDN HIT. Each accepted request must have its own delivered event UUID and native request ID.

Joining uses a Middleware-generated UUID, the actual emission envelope’s requestId, and exact equality with a genuine native request record. Browser-supplied labels and receipts cannot manufacture a verified join. Missing delivery stays pending; an incomplete manually stepped session is partial, not a failed completed suite.

R32 remains a workaround with partial customer coverage. This bounded exercise does not establish a universal logging contract, customer cookie semantics, a delivery SLA or production cost. Ticket validation adds a pre-cache collector call in browser mode; that is separate from the independently counted content-origin call.
